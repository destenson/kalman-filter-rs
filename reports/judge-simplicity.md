## Per candidate

### B

**Strengths**
- The problem is mirrored by the types: `Model` (validated, immutable F/Q/H/R) and `Estimate` (x, P) are values, `predict`/`update`/`correct` are pure prior→out functions, and the shell owns the spares and swaps only on success (B/src/filter.rs:31-98, :143-243, :356-367). Atomicity is therefore structural, not a comment: a failed step leaves the prior untouched because it was never written.
- Scratch buffers have one meaning each (B/src/filter.rs:103-113: `fp`, `a`, `ap`, `pht`, `k`, `kr`, `s`, `l`, `y`), so the reader never has to remember what a buffer meant three lines up. A has the opposite property (see A).
- One tolerance decides every numeric threshold: `relative_tolerance = 32·n·ε` (B/src/matrix/mod.rs:155-160), used by the Cholesky pivot test (:72-88) and the PSD test (:111-140). A has three; C has one too, so this separates B and C from A.
- Construction is one validated path split along the two invariants: model matrices through `Model::new`, initial estimate through `Estimate::new` (B/src/filter.rs:42-51, :85-90). The checks are four named pure functions (B/src/validation.rs:11-56).
- Public surface is the smallest: seven methods, and `model()` is `pub(crate)` (B/src/filter.rs:351), so the four model accessors A exposes (A/src/filter.rs:174-191) never become API.
- Singular PSD input is accepted by a pivoted LDLᵀ elimination rather than plain Cholesky (B/src/matrix/mod.rs:102-140) — the algorithm is explained in six lines of comment and needs no tolerance zoo.
- Probe evidence: each feature landed as an extension of an existing part. Control became a `Model` field, one kernel and a threaded parameter (B__control-input.diff:37-63, :168); the observer became a shell hook called after `commit` (B__observer-hook.diff:110-130); the smoother became one more pure step beside `predict`/`update` (B__rts-smoother.diff:143-180). No probe forced a change to the type's generics or a second entry point for the same work.

**Defects**
- `[critical]` The tree does not build. `tests/functional_tests.rs` still imports `kalman_filters::filter::KalmanFilter` un-gated (B/tests/functional_tests.rs:7), so `cargo build --all-targets` fails and `cargo test` runs nothing (metrics.md:6 build ❌; full-test-status.md:14). BRIEF.md:12-13 makes a green all-targets build a hard constraint, and this is a half-finished mechanical migration, not a stylistic choice.
- `[major]` Two public modules with nothing in them: `pub mod matrix` and `pub mod validation` (B/src/lib.rs:42,52) while every item in both is `pub(crate)` (B/src/matrix/mod.rs:14-17, B/src/validation.rs:11-49). The public surface promises two modules a user cannot call.
- `[major]` A second matrix API survives in the same module: the trait shim (B/src/matrix/mod.rs:13-14) is 109 lines whose own header says "keep the old behaviour on purpose" (B/src/matrix/legacy.rs:1-7) and whose `invert` still uses the absolute epsilon pivot the spec rejects (B/src/matrix/legacy.rs:76). A newcomer has to know which of the two ways to multiply a matrix is the real one.
- `[minor]` `correct` is `pub(crate)` and documented as "shared by every filter whose update is linear or linearized" (B/src/filter.rs:186-197), but its only caller is `update` (B/src/filter.rs:181). That is a seam built for a callers list of one.
- `[minor]` `update` moves `ws.y` out with `mem::take` and puts it back after `correct` returns (B/src/filter.rs:176-183). The reason is a borrow conflict, not the algorithm; a reader must notice that `y` briefly stops existing.
- `[minor]` `commit(step: &str, result)` takes a label used only for a `log::debug!` string (B/src/filter.rs:356-367).
- `[minor]` `Estimate`'s doc claims P is "symmetric PSD … preserved by the step functions" (B/src/filter.rs:75-76), but the steps only check finiteness (B/src/filter.rs:245-247). With an ill-conditioned S that claim is unenforced; the differential run shows a 7.5e-1 relative disagreement on one such case (difftest.md:15), consistent with the gain losing digits.
- `[minor]` Two scratch types and fourteen buffers (B/src/filter.rs:103-113, :136-160). The second one is justified (the n×n factor has no home in the m×m workspace) but doubles the "what is scratch for" reading.
- `[minor]` No `DESIGN_NOTES.md` (required by SPEC.md:296-297), and `docs/DESIGN.md:1-30` still describes the removed builder and the two-backend design, so the repository's own design document now contradicts the code.
- `[minor]` `InvalidInput(&'static str)` (B/src/error.rs:29) makes caller matching stringly: B's own tests match `KalmanError::InvalidInput("z")` (B/src/filter.rs:427,438). C's two specific variants are easier to match.

**Ideas worth grafting** (these are the reasons to keep B's shape)
- The `Model`/`Estimate` split with steps that take `prior` and write `out`, so a step cannot half-commit (B/src/filter.rs:143-243).
- The shell that only swaps on success and holds logging outside the math (B/src/filter.rs:356-367).
- One `relative_tolerance` helper consumed by every numeric decision (B/src/matrix/mod.rs:157-160).
- The pivoted-LDLᵀ acceptance test that admits singular PSD matrices (B/src/matrix/mod.rs:111-140).
- `predict_with_control` returning `DimensionMismatch` rather than silently applying u = 0 on a filter built with B (B__control-input.diff:160-175) — the "no silently ignored input" stance expressed in the API.

### C

**Strengths**
- The least invented machinery: the filter is nalgebra, so there are no bespoke kernels to learn; each step is a handful of in-place library calls with the equation written above it (C/src/filter.rs:195-259).
- Dimensions are not stored as fields: `x`, `P`, `H`, `B` carry their own shapes (C/src/filter.rs:169-176, :246), so n and m cannot drift out of sync with the slices. A and B both store n and m alongside the buffers (A/src/filter.rs:35-45, B/src/filter.rs:31-38).
- One knob for every numeric decision: `rel_tol = 100·ε` (C/src/filter.rs:60-66), used by the symmetry test (:322), the PSD shift (:334) and the Cholesky pivot test (:238). Nothing else in the filter invents a threshold.
- The constructor establishes the symmetry invariant instead of assuming it: `symmetric_psd` returns the repaired matrix and P is symmetric from construction (C/src/filter.rs:313-336); A and B copy `p0` through unchanged (A/src/filter.rs:152, B/src/filter.rs:89) while documenting symmetry as an invariant.
- The new error variants are the most specific of the three: `ZeroDimension` and `NonFiniteInput` (C/src/error.rs:28-31) name the two conditions without a string payload.
- `DESIGN_NOTES.md` is complete and honest: architecture, every decision with the rejected alternative, a "what fought back" section, known weaknesses, and a migration table (C/DESIGN_NOTES.md:3-139). It is the only candidate a newcomer can read before the code.
- Three of four probes landed inside `src/filter.rs` without touching the type's public surface, and the smoother is a free function over `Clone` plus the public accessors (C__rts-smoother.diff:121-136), so it adds no new filter method and widens only two helpers to `pub(crate)`.
- The code is the smallest of the three (747 LOC, `src/filter.rs` 421 including 83 test lines, `src/matrix/mod.rs` 94) and reads as one algorithm rather than a framework.

**Defects**
- `[major]` The public type's generics are load-bearing reading: `LinearKalmanFilter<T: RealField + Copy, N: Dim = Dyn, M: Dim = Dyn>` carrying `where DefaultAllocator: FilterAllocator<N, M>` on the struct, the workspace, the impl, and every free helper (C/src/filter.rs:50-58, :74-77, :90-93, :111-114, :300-306). Anyone touching the filter must reproduce that bound. The control probe had to widen the public `FilterAllocator` trait to a third dimension (C__control-input.diff:123) — a feature changed the shape of the type rather than adding to it. That is the strongest signal against C's structure.
- `[major]` A 94-line compatibility shim is part of the public API (C/src/lib.rs:37, C/src/matrix/mod.rs:1-9, :36, :47) and it is lossy and silent: every value round-trips through `f64`, and `matvec`/`matmul` swallow a length error and leave the output untouched (`if let (Ok(a), Ok(x)) = … { let _ = store(…) }`, C/src/matrix/mod.rs:51-69). Two matrix universes are exposed, one of which cannot report failure.
- `[major]` `linear` is not a module in its own right; it is another name for `filter` (C/src/lib.rs:34,57). Anything added to `filter.rs` becomes public `linear` API, and the smoother probe had to move to a top-level module for that reason (C__rts-smoother.diff:1-6). One name would be enough; two names that are the same thing make "where does this go" a judgement call.
- `[minor]` nalgebra's by-value `Cholesky` leaks into the workspace as `Option<OMatrix<T, M, M>>` with a take/unpack dance (C/src/filter.rs:104-106, :226, :240, :247). The invariant "`s` is None only during that move" has to be read and believed.
- `[minor]` `covariance()` returns nalgebra's column-major storage and is documented as row-major "because P is exactly symmetric" (C/src/filter.rs:183-187). That is a real invariant, but the accessor's contract now depends on a property of the data, not on the storage.
- `[minor]` The ergonomic builder infers the dimensions from slice lengths with `f.len().isqrt()` and `h.len().checked_div(n)` (C__ergonomic-constructors.diff:296-297), carries `PhantomData<fn() -> (N, M)>` to keep the filter's dimension types (:251), and needs six overlapping `From` impls (:147-180) to make `impl Into<Covariance<T>>` accept every shape. A malformed F produces a dimension error about a guessed (n, n) rather than about F.
- `[minor]` The observer probe splits the one update body into `update_inner<const OBSERVE: bool, F>` with a dummy closure on the unobserved path (C__observer-hook.diff:109-110, :148). It works and the report says why, but a newcomer now has two entry points and a compile-time bool to hold while reading "the" update.
- `[minor]` `model()` returns a four-tuple behind `#[allow(clippy::type_complexity)]` (C/src/filter.rs:190-193); the allow is the code admitting the signature is awkward.
- `[minor]` The smoother probe computes `checked_mul` for the output lengths and then only uses it as an allocation hint: the comment says "an unrepresentable length cannot reach the allocator" (C__rts-smoother.diff:259-262), but `Vec::with_capacity(states.unwrap_or(0))` discards the overflow and the loop then grows the vector anyway. A comment asserting what the code does not do — exactly what this lens penalises.
- `[minor]` `README.md` and `docs/DESIGN.md` still document the removed `KalmanFilterBuilder`; C's own probe notes admit the README is stale (C__ergonomic-constructors.notes.md).

**Ideas worth grafting**
- One `rel_tol` constant for symmetry, definiteness and pivots (C/src/filter.rs:60-66), with the three uses spelled out in comments.
- The PSD test as "`A + tol·tr(A)·I` admits a Cholesky factor" (C/src/filter.rs:308-336): one factorisation decides definiteness relative to the matrix's own scale, and the singular case falls out of the trace check.
- Deriving dimensions from the data (matrices own their shapes, C/src/filter.rs:169-176) so no stored `n`/`m` can disagree with the buffers.
- The design-notes skeleton: decisions with rejected alternatives, "what fought back", known weaknesses, migration table (C/DESIGN_NOTES.md:17-127).
- The observer as a per-call argument (`update_with_observer(z, &mut F)`, C__observer-hook.diff:140-146) so `Clone`, `Debug` and `Send` on the filter are untouched.

### A

**Strengths**
- The whole algorithm is in one file and reads top to bottom: `predict` (A/src/filter.rs:195-220) and `update` (:228-297) are laid out as the equations, with the buffer roster documented once (A/src/filter.rs:48-60). For a small core, this is the easiest file of the three to read start to finish.
- Atomicity by pointer swap: the candidate estimate is built in workspace buffers and swapped in only after the checks (A/src/filter.rs:299-303). No copy, no half-written state.
- Upper-triangle-only kernels plus `mirror_upper` make symmetry exact by construction instead of averaging (A/src/matrix/mod.rs:70-99). `axpy`, `matmul`, `cholesky_solve_rows` keep the loops free of bounds checks by iterating with `chunks_exact`/`zip` (:8-10).
- The PSD acceptance test is the most carefully argued of the three: scale to a unit-diagonal correlation matrix, shift the diagonal by a relative tolerance, then Cholesky (A/src/validation.rs:15-61). Acceptance is invariant under a change of units in any component, and singular PSD passes.
- No logging or metrics anywhere in the owned core (grep of `src/filter.rs`, `src/matrix/`, `src/validation.rs` finds none), so Q4 is satisfied by construction rather than by discipline.
- No dimension generics and no public helper traits: the type takes only `T`.

**Defects**
- `[critical]` The post-step PSD check cannot do what its comment says. `variances_consistent` (A/src/filter.rs:75-84) is a set of necessary conditions (non-negative variances, |p_ij| ≤ √(p_ii p_jj)), and the comment above its use says the step reports S as singular "rather than commit an invalid covariance" (A/src/filter.rs:289-291). A matrix can satisfy those conditions and still be indefinite, and the candidate's own test is red at its tip: `P not PSD` with λ_min = −9.8e-3 (f32) and −1.19e-15 (f64) (A/tests/linear_kf_robustness.rs:115,129-130; _evidence/finding-A-psd.md:12-24; full-test-status.md:13). The comment states a guarantee the code does not provide.
- `[major]` Three different relative tolerances decide three closely related questions: `singular_tol = 64·m·ε` for pivots (A/src/filter.rs:71-73), `64·n·ε` slack in the cheap PSD screen (:79-80), and `16·n·ε` in construction (A/src/validation.rs:11). A reader cannot tell which is authoritative or why they differ, and the smoother probe reuses the pivot tolerance for an n×n matrix, where the parameter is named `m` (A/src/filter.rs:71; A__rts-smoother.diff:123).
- `[major]` Four scratch buffers change meaning inside a single step: `p` is the candidate covariance (:53) and the construction-time PSD scratch (:141); `s` is the PSD scratch for R (:144), then S (:248), then its Cholesky factor (:253); `kt` is HP (:247) then Kᵀ (:257); `ap` is FP (:202) then (I−KH)P (:277). The comment map at A/src/filter.rs:51-60 is the only record of this, and every reader of `update` must hold it.
- `[major]` The compatibility layer is a lie about what `DefaultBackend` is: `use crate::matrix as DefaultBackend;` (A/src/extended.rs:64) makes the module answer to the removed backend type's name, so `DefaultBackend::matmul(...)` calls a free function. This is clever zero-code compatibility, but anyone reading or grepping the out-of-scope modules is misled.
- `[major]` Three public paths to one type: `kalman_filters::LinearKalmanFilter`, `kalman_filters::filter::LinearKalmanFilter`, and `kalman_filters::linear::LinearKalmanFilter` (A/src/lib.rs:38,62,63, plus the facade at A/src/filter.rs:27-29). For a rewrite whose point is "one linear filter", exposing it under three names is the wrong first impression.
- `[minor]` A posterior that loses PSD is reported as `KalmanError::SingularMatrix` (A/src/filter.rs:292-294), the same variant as a singular S. A caller that handles "S was singular" now also silently handles "the covariance I just committed is invalid", which is not the same condition.
- `[minor]` `check_len(slice, rows, cols, len)` takes the expected product twice (A/src/filter.rs:91-97), and every length error is reported as `actual: (slice.len(), 1)`, so a wrong-sized p0 claims to be a one-column matrix. B (B/src/validation.rs:30-33) and C (C/src/filter.rs:288-293) make the same misreport; it is a family wart, but A's version also duplicates the product.
- `[minor]` A kernel silently ignores one of its dimensions: `add_transpose_matmul_upper` takes `k` and discards it (A/src/matrix/mod.rs:82-83), and `matvec`/`matmul` ignore `_rows`/`_m` (:45, :52), trusting the slice lengths (documented at :8-10). A wrong argument truncates the sum instead of failing, and the crate-wide `#![allow(unused, non_snake_case)]` (A/src/lib.rs:31) keeps the compiler quiet about it.
- `[minor]` `invert_matrix` is `pub` inside a `pub(crate)` module (A/src/matrix/mod.rs:191, A/src/lib.rs:41): crate-visible in effect, public in intent, and it exists only for the out-of-scope filters (A/src/matrix/mod.rs:5).
- `[minor]` The observer probe required a hand-written `Clone` whose own doc says the clone silently drops the observer (A__observer-hook.diff:95-110). Cloning a filter then behaves differently from cloning a filter without one, and nothing in the type says so.
- `[minor]` Eleven public methods to SPEC's seven: four model accessors are added (A/src/filter.rs:174-191) that no in-scope code needs, and the crate-wide `allow(unused)` hides whether anything calls them.
- `[minor]` No `DESIGN_NOTES.md` (SPEC.md:296-297). `docs/DESIGN.md:1-30` still describes the removed builder and the two-backend design, and the own-code-versus-nalgebra decision is recorded nowhere, which matters because A chose own-code and the reader has to infer why.

**Ideas worth grafting**
- `is_psd` via correlation scaling plus a relative diagonal shift (A/src/validation.rs:26-61): one routine that accepts every PSD matrix at every scale and rejects anything below the relative tolerance.
- Upper-triangle-only products with a single `mirror_upper` (A/src/matrix/mod.rs:70-99): exact symmetry with no averaging and half the work.
- `variances_consistent` as a cheap O(n²) screen before an O(n³) check (A/src/filter.rs:79-84) — useful only as a screen, never as the guarantee, which is exactly the distinction A's comment loses.

## Best skeleton
B's. Under this lens the question is how much a newcomer must hold to make a correct change, and B is the only candidate whose parts correspond to parts of the problem: a validated model, a validated estimate, pure steps that take a prior and write a posterior, and a shell that decides when a result becomes current. Each of the four probe features landed in one of those parts without reshaping the type; C's control probe changed the public type's dimension parameters and its allocator trait, and A's observer probe forced a hand-written `Clone` with new semantics. B also keeps one tolerance knob, one meaning per scratch buffer, and the smallest public surface (seven methods, `model()` crate-private), all of which reduce what must be remembered at a call site. The recommendation comes with two conditions: fix the un-gated import that breaks `cargo build --all-targets` (B/tests/functional_tests.rs:7), and delete the `default backend` trait shim once the nonlinear filters are rebuilt (B/src/matrix/mod.rs:13-14, B/src/matrix/legacy.rs). B's structure is worth keeping; its finishing is not.

## Grafts
Into B's skeleton:
- From A: the correlation-scaled PSD acceptance test (A/src/validation.rs:26-61), used in `Model::new`/`Estimate::new` in place of B's `is_symmetric_psd` — it is the same idea (relative tolerance) but stated once in unit-free terms and it accepts singular PSD without a pivot loop.
- From A: upper-triangle-only products and `mirror_upper` (A/src/matrix/mod.rs:70-99) as B's `mul_bt`/`symmetrize` replacement, so exactly-symmetric P is structural rather than the average of two roundings.
- From A: keep `variances_consistent` (A/src/filter.rs:79-84) as a cheap screen *in addition to*, never instead of, a sufficient check — this is the one place B and A can both be improved: B has neither, A has only the screen.
- From C: the single `rel_tol` constant and the comment style that names the three uses (C/src/filter.rs:60-66) — B's `relative_tolerance` is the same idea; adopt C's statement of what the number means ("100·ε, compared against the scale of the matrix being tested, never an absolute threshold").
- From C: the PSD test as "`A + tol·tr(A)·I` is factorable" (C/src/filter.rs:308-336) as the concrete alternative to B's pivoted elimination if a simpler routine is wanted; both accept singular PSD, C's is four lines.
- From C: the per-call observer (`update_with_observer(z, &mut F)`, C__observer-hook.diff:140-146) instead of B's stored boxed observer, so `Clone`, `Debug`, `Send` and `Sync` on the filter stay what they were.
- From C: the design-notes structure (C/DESIGN_NOTES.md:17-127), including the "what fought back" and "known weaknesses" sections — B needs a `DESIGN_NOTES.md` anyway and C's is the model to copy.
- From B itself, keep: the `Model`/`Estimate` split with prior→out steps (B/src/filter.rs:143-243), the swap-on-success shell (:356-367), `predict_with_control` erroring instead of silently applying u = 0 (B__control-input.diff:160-175), and `model()` staying crate-private (B/src/filter.rs:351).

## Where the numbers mislead
- LOC (C 747, A 965, B 1061): C's lower count is mostly nalgebra doing the linear algebra and `validation.rs` being deleted. The work it hides is 288 lines in A's `src/matrix/mod.rs` that a newcomer must read either way — as code in A, as a dependency's API in C. A lower LOC here means "someone else's code", not "less to hold".
- Probe churn (C 563, B 585, A 713 average): churn counts lines, not concepts. C's control probe is 418 lines and changed the public type from two dimension parameters to three plus the public allocator trait (C__control-input.diff:123,155); B's 374 lines left the type's shape alone. Conversely A's 601-line control probe is mostly a second constructor and a second predict entry point (A__control-input.diff:167), which is large but flat.
- Lint counts (A 160, B 149, C 137): all three inherit the baseline's crate-wide `#![allow(unused, non_snake_case)]` (A/src/lib.rs:31, B/src/lib.rs:32, C/src/lib.rs:27), so unused items, ignored parameters and the empty public modules are invisible. A's discarded `k` argument (A/src/matrix/mod.rs:83) and B's `pub mod matrix` with no public items (B/src/lib.rs:42) cost nothing in that column, which is why the lowest lint count belongs to the candidate with the most public dead surface.
- Test counts (A 140, B 144, C 137 passed): B's 144 coexist with a tree where `cargo test` compiles nothing, because the count is taken from `--lib` plus the frozen suite (full-test-status.md:14). A green test count and a runnable test suite are different measurements.
- `frozen⚠ 0` for all three: it says nobody edited the acceptance contract, nothing about how much a change costs.
- The differential table's `status≠` column compares error *variant names*, so B's count of 6 overstates behavioural divergence: `edge_nan_q`, `edge_zero_meas_dim`, `edge_zero_state_dim`, `edge_inf_f` and `edge_nan_measurement` are the same rejection under `InvalidInput` instead of the oracle's `NonFiniteInput`/`InvalidDimension` (difftest.md:17-21). A's 2 value disagreements and 3 status disagreements look better than B's 6, but A is the candidate measured to commit an indefinite covariance on models the differential test did not generate (finding-A-psd.md). Neither count measures how hard the code is to change.
- `full-test-status.md:15` ("C is the only candidate whose whole tree is green") is true but flattering: C reached green partly by `#![cfg(any())]`-gating four whole test files and items in three more (C/tests/core.rs:7 and the same pattern in `algorithm_validation`, `cross_validation`, `quickcheck_invariants`, `fault_tolerance_tests`, `property_tests`, `functional_tests`). SPEC.md:63-64 permits it, and A and B did it too (A/tests/core.rs:2, B/tests/core.rs:3), but a green tree full of files that never compile is not a clearer tree — a newcomer can edit them and get no feedback. The one metric that maps straight onto a newcomer's first ten minutes is B's build ❌ (metrics.md:6), and it is the one not visible in any test column.
